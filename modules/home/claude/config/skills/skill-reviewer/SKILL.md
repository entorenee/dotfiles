# Skill Reviewer

## Overview

Closes the feedback loop on a workflow. Every other skill here produces work; this one measures whether a skill is *earning its place* and edits it based on what actually happened, not on what seems sensible.

The loop:

```
run skill → transcripts accumulate → mine gate evidence → classify catches
     ↑                                                          ↓
     └────────── edit SKILL.md ←── propose ←── find patterns ───┘
                       ↓
                  record baseline in the ledger ──→ next review measures the delta
```

The ledger step is what makes this a loop rather than a one-off audit. A review that does not write down what it measured cannot be compared against the next one, and every future review restarts from zero.

**Where the two halves live, and why they are split.** Policy is committed; evidence is not.

| | Path | Reason |
|---|---|---|
| Scripts, thresholds, this file | `modules/home/claude/config/skills/skill-reviewer/` | Repo-level. They describe the skills, which every machine shares. |
| `testimony.txt` | same directory, committed | The only record that is **not** re-derivable — it is the user's memory, not the archive's. Losing it means asking the same question twice, which has already happened. |
| `LEDGER.md` | `$ARTIFACTS/skill-reviewer/LEDGER.md`, resolved from `MY_CLAUDE_ARTIFACTS_ROOT` | Measurements of one machine's transcript archive, which does not sync. Every figure in it can be regenerated by re-running the two scripts, so it is a cache, not a source of truth — and keeping it out of the Nix store means appending a row does not need a rebuild. |

## Cadence and thresholds

The single source for when a unit is due. `/system-review` reads this section; the ledger holds only measurements.

Two tiers, because run volume varies by an order of magnitude across units. A weekly review of *most* units would examine 0–1 new runs — below the anecdote floor below — and would fill the ledger with rows that bury real trends. Measured 2026-08-19 over the 30 days those units were active: `investigate` about 4.4×/week and `pre-pr` about 3.7×, with everything else far below both. The two busiest units would sustain a weekly cadence; the rest would not, and the sweep exists so the cheap tier can tell you which is which.

| Tier | Trigger | Cost | Does |
|---|---|---|---|
| **Sweep** | Weekly | ~2 min | Read the ledger against these thresholds. Report what is due. Usually "nothing." |
| **Review** | A unit crosses its threshold | ~1 session | Full workflow below, on one unit. |

| Recorded runs | Review due after |
|---|---|
| ≥ 3 | 5 new runs, **or** 45 days since that unit's newest ledger row — whichever comes first |
| < 3 | **Not eligible.** There is no pattern yet, only anecdote. If asked anyway, the finding *is* "insufficient evidence" — record that rather than manufacturing one. |

**One threshold for every eligible unit, deliberately — do not reintroduce volume tiers.** An earlier version raised the bar to 8 runs above 10 recorded runs. Two things were wrong with it. The rule read the tier off a *moving* quantity, so a unit crossing 10 between reviews silently raised its own bar: measured 2026-08-19, `pr-review` went from two runs short of due to three runs short *by being used more*, falsifying the closing note in `plans/2026-08-12-skill-system-cadence-plan.md` that predicted it would reach its threshold on its own. And the direction was backwards — the ledger's headline finding is that `investigate`, the most-used unit, carries 3× the correction rate of `pre-pr`. Volume is a reason to review sooner, not later.

The 5 is an evidence floor: enough runs to see a pattern rather than an anecdote. The 45 days is a staleness ceiling for a unit that is used but used slowly — five runs may be a year away, and the text should not go unexamined that long.

Both arms are computable from `inventory.sh` alone, which is the property that keeps the sweep to two minutes. They do not draw on the same source, though, and the difference decides when the second one can fire:

| Arm | Reads | Fires when the ledger is missing? |
|---|---|---|
| 5 new runs | `runs_since` — transcripts against the git history | Yes. Needs no ledger at all. |
| 45 days | `last_reviewed` — the newest ledger row for that unit | **No.** |

`inventory.sh` emits `last_reviewed` by parsing `LEDGER.md`; before it did, this arm named a date nothing produced and could not be executed at all. The ledger is machine-local, so on a machine that has none — or for a unit that has never been reviewed on this one — `last_reviewed` is null and the staleness arm simply cannot fire. Say that rather than treating null as "reviewed long ago"; the run-count arm carries the cadence alone in that case, exactly as the never-reviewed rule below already specifies.

**Known gap, deliberately left open:** a unit that is eligible (≥ 3 runs), never reviewed, and too slow to reach 5 runs is governed by neither arm and can wait indefinitely. Closing it means deciding what a never-reviewed unit's staleness clock starts from — most likely `changed` — and that is a cadence decision, not a defect fix. Do not close it silently as part of unrelated work.

**Runs are counted since the commit that last changed the unit, not since the last ledger row.** A skill edited last week has almost no runs against its current text, so reviewing it measures the text it no longer has. This replaces any hand-kept exclusion list: eligibility re-arms itself as runs accumulate. Step 1's `git log --follow` is where that date comes from.

**A unit with no ledger row is due at 5 runs** regardless of how many it has accumulated. Never-reviewed is not the same as recently-reviewed.

## When to Use

- "Review the `<name>` skill" / "is `<name>` actually working?"
- After a workflow has accumulated roughly 5+ real runs
- When a skill keeps producing output you correct in the same way

## When NOT to Use

- Authoring a new skill, or editing one for a reason you already know (just edit it)
- A workflow with fewer than ~3 runs — there is no pattern yet, only anecdote
- Session-level lessons that belong in memory or `CLAUDE.md` (use `/reflect`)

## The feedback path

Named explicitly, because a loop whose arms are vague does not run.

| Arm | What it is |
|---|---|
| **Signal** | Human turns at the gate: corrections, interruptions, and review-time gaps. An interruption is the strongest of the three — the human stopped the run mid-flight — and the cheapest to miss, because it carries no text. |
| **Collection** | `inventory.sh` for coverage, then `mine.jq` for gate evidence. One command each, no heroics; the alternative is reconstructing history by hand, which is why loops like this normally never run twice. |
| **Feedback** | Edits to the reviewed skill's own `SKILL.md`, each citing the run that justifies it, plus a ledger row so the next review can measure movement. |

## Workflow

### Step 1 — Fix the target and the baseline

Name the skill under review. Read `$ARTIFACTS/skill-reviewer/LEDGER.md`; if it has a previous entry for this skill, that row is the baseline and this review must report the delta against it. If not, this review *is* the baseline — say so, and do not imply a trend from a single measurement.

The ledger is machine-local and outside the repo, so on a new machine it will not exist. That is a missing baseline, not a first review: re-derive the previous figures with the two scripts before claiming any delta, and label them as reconstructed.

Also get the revision history, because "we already tightened this" is a testable claim:

```bash
git --no-pager log --follow --date=short --format='%ad %h %s' \
  -- modules/home/claude/config/skills/<name>/SKILL.md
```

Directory moves and repo-wide refactors show up here and are **not** tightenings. Check what a commit actually changed before counting it. If a file's content has never changed, say that plainly — a workflow that has run 10 times and never been revised is the finding, not a footnote.

### Step 2a — Establish coverage before counting anything

```bash
bash <skill-base-dir>/inventory.sh
```

One row per skill and slash command, with the arm each piece of evidence came from. Read the target's row first, and read the `COVERAGE` footer every time — it is what stops the next paragraph from happening again.

**A skill invoked *inside* another skill leaves no direct record at all.** On 2026-08-12 this skill reported six skills as never used, from a count that only saw Skill-tool calls and slash commands. Three of them — `dead-code-survey`, `error-triage`, `evidence-consolidation` — had run repeatedly, composed inside `regression-analysis` and `analytics-friction-analysis`. The user had to supply the correction. Two of the three still write no artifact of their own, so no amount of better scanning would have found them; they are in `testimony.txt` for exactly that reason.

Composition is not the only way to go missing. Asked again on 2026-08-17, with all four arms running, the user reported that `regression-analysis` had also run — and nothing composes `regression-analysis`. A directly-invoked entry point can still leave nothing behind, if its session predates the archive or the workflow was followed without the Skill tool at all.

So `no-evidence` means **not measured**. Every machine count is a floor. Before writing any unit down as unadopted, ask — and record the answer in `testimony.txt`, so the next run inherits it instead of asking again.

The loose fallback — grep the skill name anywhere — is not the answer either: it returns roughly one hit per transcript, because the available-skills listing is injected into every session.

**The corpus contains this review.** A session that analyses skill usage writes the invocation strings, and their grep output, into its own transcript. Plain text matching counts the review as a run — measured 2026-08-17 at 4 phantom `investigate` sessions and 1 phantom `pre-pr-autonomous`. Both `inventory.sh` and `mine.jq` pin their matches to the record shape a real invocation produces. Do not hand-roll a looser grep and trust the number.

Where the target's row lands decides whether Step 2b is worth running. **All eight verdicts are listed; a routing table missing one sends that unit down whichever branch looks closest, which is how `composed-only` got reviewed as if it were `used`.**

| Verdict | Do |
|---|---|
| `used` | Continue. Gate evidence exists. |
| `composed-only` | Continue, but attribute before editing. Every session also ran a caller, so the gate evidence is real and belongs to *some* file — just not necessarily this one. Resolve the caller question in Step 4 before proposing an edit here. |
| `subagent-only` | Stop. Every invocation came from a sidechain, so no human was ever present to gate it — there is nothing to mine, and a review would report the absence of corrections as though it meant correctness. |
| `artifact-only` / `testimony` | Read the artifacts. There is no gate evidence to mine, so a review here reports what the runs *produced*, not what the human corrected — say so rather than implying a gate analysis happened. |
| `unadopted` | Stop, and do **not** ask. The user has already said it has not run; that question is closed in `testimony.txt`. Report it as declined, not as unmeasured. |
| `reachable` | Review the caller instead, and read this skill's sections as they were exercised inside it. |
| `no-evidence` | Stop and ask. |

The verdicts are ranked, not independent: a real session outranks testimony, so a unit whose `testimony.txt` line says `unadopted` but which now shows a session reads as `used`. That is the precedence working — evidence beats memory — but it means the testimony line has gone stale. Correct it when you see it, rather than letting the `VIA` column keep reporting a claim the run count already refutes.

### Step 2b — Collect the gate evidence

`mine.jq` takes a whole transcript as a raw string and emits one JSON object per session, or nothing when the skill never appears — so it is safe to point at everything.

The file-selection grep below is deliberately loose. It only pre-filters; `mine.jq` re-validates every record and emits nothing for a file that merely mentions the name, so a loose selector can waste a little parsing but cannot inflate a count.

```bash
D="$HOME/.claude/projects"
M=<skill-base-dir>/mine.jq          # absolute path; cwd drifts between calls
OUT="$TMPDIR/skillrev"; mkdir -p "$OUT"
SKILL=investigate

# Slash commands appear as <command-name>; Skill-tool calls as "skill":"<name>".
grep -rl "\"skill\":\"$SKILL\"\|<command-name>/$SKILL<" "$D" > "$OUT/files.txt"

while read -r f; do
  jq -sR -f "$M" --arg skill "$SKILL" "$f" 2>/dev/null \
    | jq -c --arg p "$(basename "$(dirname "$f")")" '. + {project:$p}'
done < "$OUT/files.txt" > "$OUT/$SKILL.jsonl"

# `// 0` on every `add` (the idiom mine.jq already uses internally): with no
# matching sessions `add` is null, and `null|round` aborts the whole aggregate.
# A zero-session result is a finding this skill wants reported, not a jq error.
jq -s '{sessions:length, invocations:(map(.invocations)|add // 0),
        gate_turns:(map(.gate_turns)|add // 0), interruptions:(map(.interruptions)|add // 0),
        corrections:(map(.corrections)|add // 0), review_min:(map(.review_minutes)|add // 0|round)}' \
  "$OUT/$SKILL.jsonl"
```

Per-session detail, corrections, and interruption context:

```bash
jq -sr 'sort_by(.first_invoked)[] | "\(.first_invoked[0:10])  gates=\(.gate_turns) int=\(.interruptions) corr=\(.corrections) med=\(.median_gap_min//"-")m"' "$OUT/$SKILL.jsonl"
jq -sr '.[] | .first_invoked[0:10] as $d | .gates[] | select(.correction) | "── \($d)\n\(.text[0:400])\n"' "$OUT/$SKILL.jsonl"
jq -sr '.[] | .first_invoked[0:10] as $d | .interrupts[] | select(.stopped) | "── \($d)\n\(.stopped[0:400])\n"' "$OUT/$SKILL.jsonl"
```

**Read the interruption contexts even when the correction list looks rich.** `.stopped` is what the run was saying when it was cut off, and it localizes the *moment* the workflow loses the human — which a correction, arriving one turn later and phrased as a request, usually does not.

### Step 3 — Classify every catch

The keyword filter is deliberately over-inclusive. Read each hit and assign one:

| Class | Meaning |
|---|---|
| `[GATE CAUGHT]` | The human caught something wrong before it landed. The skill should have caught it. |
| `[AI SELF-CAUGHT]` | The run corrected itself, unprompted, later in the same session. Still a defect — it burned tokens and could have gone the other way. |
| `[FALSE POSITIVE]` | Keyword hit, no correction. Discard, but count them; a high rate means the filter needs work. |
| `[UNRESOLVED]` | Raised, never settled. The most dangerous class, because nothing in the transcript says who was right. |

Only `[GATE CAUGHT]` and `[AI SELF-CAUGHT]` are evidence for an edit.

### Step 4 — Find the pattern, and test the obvious explanation

Group the catches by mechanism, not by topic. Two findings about different files that share a mechanism are one pattern.

Then answer these three in writing. They are the questions that make this a review rather than a list:

1. **Is there a pattern in what it gets wrong?** Name the mechanism, not the symptom.
2. **Is the checklist testing the right things, or the easy things?** For each major section of the skill, find a run where it fired. A long, detailed section with zero hits across every run is testing the easy thing. Meanwhile check whether the real failure modes are addressed anywhere at all.
3. **Is review time trending down — and should it be?** Falling review time is only good if the error rate falls with it. If corrections held flat or rose while gaps shrank, that is automation complacency and the correct response is a review floor that does not decay, not a congratulation.

**A correction during a composed run may belong to the callee.** `inventory.sh` prints the composition graph's reachability in the `VIA` column. When the reviewed skill delegates — `pre-pr` → `code-hygiene` → `comment-review`, the four evidence skills → `evidence-analysis-core` — check which file the failing instruction actually lives in before proposing an edit. Fixing the caller for a defect in shared substrate leaves the defect live in every other caller, and the evidence family cites itself almost completely, so this is the common case there rather than the exotic one.

**Normalize before claiming a trend.** Raw correction counts track how much work was done, not how error-prone the skill is; divide by gate turns. Compare an early window against a recent one rather than eyeballing the series.

### Step 5 — Propose edits

Every proposed edit carries the run and the quote that justifies it. An edit you cannot attach evidence to is a guess, and guesses are how a checklist grows long while staying weak.

Weight the edits by where the evidence actually is:

- **A gate the human keeps supplying by hand belongs in the skill.** Repeated interruptions at the same point in the workflow mean a missing hand-back, not an impatient user. This is the highest-value edit class and the easiest to overlook, because it looks like friction rather than error.
- **Prefer deleting to adding.** A section with no hits across every run is a candidate for removal. Checklists fail by dilution far more often than by omission — if the review only ever adds, it is making the next review harder.
- **Do not add a rule the evidence does not support**, however sensible it sounds. That is the failure mode this whole skill exists to prevent.
- **A skill states the method; the project states the facts.** Never name a specific repository, package, path, or example file in a `SKILL.md` — those go stale silently, they narrow the skill to one codebase, and this repository is public. Measured 2026-08-19: four such citations across `feature-plan` and `feature-design-doc` pointed at plan documents, three of which no longer existed, and they were the *only* concrete anchor for the commit-cadence rule. Where a skill needs a project fact, tell it to read that fact from the project's own `CLAUDE.md` or manifest — which is both more resilient and the only version that stays correct when the project changes.
- **Say which edit you expect to fail.** Usually the one asking the human to hold a standard against their own convenience. Naming it now is what makes the next review able to check it.

Present the edits and get approval before touching the file. Then apply them.

**Put the prediction in the commit message, not only in the ledger.** The ledger is git-ignored and re-derivable; a prediction is neither. Written into the commit that carries the edits, it survives the ledger and lands on a path the next review already walks — Step 1 runs `git log --follow` over the same file. Hand the user a `Expected to fail: <the fragile edit>` line to paste when they commit.

### Step 6 — Write the ledger row

Append to `$ARTIFACTS/skill-reviewer/LEDGER.md`, creating it if this machine has none. Without this the next review has no baseline and the loop is open again.

```markdown
## <skill> — <YYYY-MM-DD>

| Metric | This review | Previous | Delta |
|---|---|---|---|
| Runs analyzed | | | |
| Gate turns | | | |
| Corrections / gate turn | | | |
| Interruptions | | | |
| Median gap (min) | | | |

**Patterns:** <mechanism, one line each>
**Edits applied:** <n> — <one line each>
**Expected to fail:** <the fragile one, and why>
**Next review after:** <n> more runs
```

### Step 7 — Report

State what changed, what you deliberately did not change, and the one measurement that would prove the edits worked. Remind that skill edits are store-symlinked and need `make rebuild` with all Claude sessions quit.

## Rules

- **Every edit cites a run.** No evidence, no edit — this skill has no license the others lack.
- **No arm sees everything, so "no data" is never "unused."** Report the arms that returned nothing alongside the ones that found something, and ask before recording a unit as unadopted. When the user answers, write the answer into `testimony.txt` so the next run cannot repeat the question — or the mistake.
- **Every count states which matcher produced it.** A number from a hand-rolled grep is not comparable to one from `inventory.sh` or `mine.jq`, and the archive contains this review's own output.
- **Never infer a trend from one review.** The first run of this skill on any skill is a baseline and must be labeled as one.
- **A revision in `git log` is not a tightening** until you have read what it changed; moves and renames dominate the history.
- **Count deletions as wins.** Report lines removed alongside lines added.
- **Interruptions outrank corrections** as evidence, and are reported even when their count is the only thing that changed.
- **Do not run `git add` or `git commit`.**
